# KAIDEN Academic Orders Hub — агрегатор и автоматизация заказов

## Контекст

Периодически выполняются заказы на подготовку учебных и исследовательских материалов: курсовые, дипломные работы, статьи и смежные задачи. Сам производственный workflow уже существует; основная проблема находится раньше — поиск и первичная обработка заказов.

Заказы распределены между несколькими платформами. Неудобство:
- нужно держать профили на множестве площадок;
- постоянно проверять новые предложения;
- вручную сравнивать их;
- отбрасывать неподходящие;
- следить за статусами и сообщениями;
- переключаться между несколькими интерфейсами.

Цель — максимально убрать этот операционный шум и подключать человека преимущественно в момент, когда действительно требуется переговорная или экспертная работа.

## Концепция

Создать **KAIDEN Academic Orders Hub** — единый внутренний центр мониторинга заказов.

Принцип:

`Platforms → Collectors/Adapters → Normalization → AI Triage → Unified Inbox → Human Negotiation → Existing Production Pipeline`

ИИ не должен бесконтрольно «сидеть в браузере и делать всё». Система должна состоять из детерминированных адаптеров и правил, а browser automation использоваться как fallback для площадок, где нет подходящего API, email/webhook/RSS или иного стабильного интерфейса.

## 1. Platform adapters

Для каждой площадки создаётся отдельный адаптер.

Приоритет способов интеграции:

1. официальный API / webhook;
2. email-уведомления;
3. доступный экспорт / feed;
4. разрешённый polling публичных/доступных данных;
5. browser automation — только если другие варианты отсутствуют и это допускается правилами площадки.

Каждый адаптер переводит данные площадки в общую модель.

## 2. Unified Order

Нормализованная сущность заказа:

- platform;
- external_id;
- url;
- title;
- description;
- subject/domain;
- work_type;
- deadline;
- budget;
- pages/volume;
- originality requirements;
- special requirements;
- customer metadata, если доступно и необходимо;
- discovered_at;
- platform_status;
- local_status;
- AI score;
- AI explanation;
- duplicate fingerprint.

Это позволяет перестать мыслить интерфейсами конкретных сайтов: внутри системы все заказы становятся одинаковыми объектами.

## 3. AI Triage

ИИ получает уже извлечённый и нормализованный заказ, а не самостоятельно исследует интерфейс сайта без необходимости.

Задачи AI:
- классифицировать тематику;
- определить тип работы;
- извлечь требования;
- оценить соответствие заданным критериям;
- отметить риски и недостаток данных;
- обнаружить потенциальные дубликаты;
- подготовить короткое summary;
- ранжировать очередь.

Пример результата:

```text
Order #...
Тип: дипломная работа
Тематика: ...
Срок: ...
Бюджет: ...
Fit score: ...
Почему интересно: ...
Риски: ...
Не хватает информации: ...
Рекомендация действия: review / skip
```

AI score не должен автоматически принимать коммерческие обязательства.

## 4. Rule Engine перед AI

До LLM желательно применять дешёвые детерминированные фильтры:

- минимальный бюджет;
- допустимый срок;
- тематики;
- типы работ;
- стоп-слова;
- география/язык при необходимости;
- статус площадки;
- blacklist/whitelist;
- дедупликация.

Это сокращает количество ненужных AI-вызовов и делает поведение системы объяснимее.

## 5. Unified Inbox

Один интерфейс вместо пяти и более сайтов.

Представления:
- New;
- High Fit;
- Needs Review;
- Negotiation;
- Accepted;
- Rejected;
- Expired;
- Archived.

Карточка должна показывать исходную площадку, требования, сроки, бюджет, AI summary, причины оценки и кнопку перехода к оригиналу.

## 6. Human-in-the-loop

Критическая граница автоматизации:

Система может самостоятельно:
- собирать;
- нормализовать;
- фильтровать;
- классифицировать;
- ранжировать;
- уведомлять;
- готовить черновики ответов.

Человек подключается для:
- переговоров;
- уточнения требований;
- согласования стоимости/сроков;
- принятия обязательств;
- спорных ситуаций.

Автоматическую отправку сообщений/откликов следует включать только для конкретных площадок и сценариев, где это разрешено и безопасно; предпочтительно начинать с draft-only режима.

## 7. Browser Worker

Для площадок без пригодной интеграции можно выделить отдельный браузерный профиль/worker.

Его роль:
- открыть разрешённые страницы;
- проверить список новых заказов;
- извлечь структурированные поля;
- проверить входящие сообщения/статусы;
- передать данные в Hub.

Архитектурно browser worker должен быть изолирован от AI decision layer.

`Browser → Extractor → Structured Event → Rules/AI`

То есть модель не должна каждый раз импровизировать, куда кликать. Для каждой площадки лучше иметь воспроизводимый сценарий с селекторами, проверками состояния, таймаутами, журналом ошибок и скриншотом/HTML snapshot при сбое.

Нужны:
- отдельные browser profiles;
- безопасное хранение сессий;
- rate limiting;
- retry policy;
- детектирование изменения интерфейса;
- audit log;
- ручное восстановление при CAPTCHA/2FA/изменении условий входа.

Не следует проектировать обход CAPTCHA, антибот-защиты или ограничений площадки.

## 8. Notification Layer

Тебе не нужно постоянно открывать Hub.

Система уведомляет только о событиях заданного уровня, например:

**Найден подходящий заказ**
- площадка;
- тема;
- бюджет;
- дедлайн;
- краткие требования;
- fit score;
- риски;
- ссылка «Открыть заказ».

Канал уведомления может быть Telegram.

## 9. Состояния заказа

Пример state machine:

`DISCOVERED → FILTERED → AI_REVIEWED → HUMAN_REVIEW → NEGOTIATION → ACCEPTED → PRODUCTION → DELIVERED → CLOSED`

Альтернативные ветки:
`FILTERED_OUT`, `REJECTED`, `EXPIRED`, `CANCELLED`.

Так Hub в дальнейшем сможет передавать принятый заказ в уже существующий производственный workflow.

## 10. MVP

### Этап 1 — наблюдение

Подключить 1–2 площадки.

Только:
- сбор заказов;
- нормализация;
- rule filtering;
- AI summary/score;
- единая очередь;
- Telegram notification.

Никаких автоматических откликов.

### Этап 2 — переговорный ассистент

Добавить:
- сбор сообщений;
- единый контекст заказа;
- AI draft ответа;
- human approval;
- фиксацию договорённостей.

### Этап 3 — handoff

После принятия заказа автоматически создавать объект в существующем production pipeline:
- требования;
- deadline;
- договорённости;
- материалы;
- источники;
- статус.

### Этап 4 — расширение

Подключать следующие площадки через adapters, не переписывая Core.

## Что важно не делать

- Не строить всю систему как один гигантский browser-agent.
- Не давать LLM самостоятельно принимать финансовые обязательства.
- Не хранить пароли в промптах или исходном коде.
- Не пытаться обходить CAPTCHA/антибот.
- Не смешивать platform-specific scraping с бизнес-логикой.
- Не начинать сразу с пяти площадок.
- Не автоматизировать производство работы заново, если этот pipeline уже решён.

## Архитектурная формула

> **Не “ИИ работает на пяти сайтах вместо меня”, а “пять площадок превращаются для меня в одну нормализованную очередь, которую ИИ предварительно разбирает”.**

Это отдельное внутреннее направление KAIDEN и потенциально самостоятельный инструмент автоматизации.
